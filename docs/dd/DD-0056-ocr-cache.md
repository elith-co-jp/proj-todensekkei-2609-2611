# DD-0056: 文字の読み取りの結果を残し、図面の解析し直しを速くする

- 状態: レビュー中
- 作成日: 2026-11-28
- 関連文書: [DD-0012](DD-0012-speed-and-ci.md)（解析の高速化）・[DD-0039](DD-0039-analysis-jobs.md)（裏の解析）

## 1. 背景と測定

アプリの処理のどこに時間と計算がかかっているかを測った（4 コアの Linux、Python 3.12）。

| 処理 | 時間 |
| --- | --- |
| 画面の API（回路・シミュレーション・論理図・デモ・矛盾チェック・図面の一覧など 16 本、紙芝居 6 枚） | どれも 60 ms 以下 |
| 図面の解析（合成図面 6 枚、記号は正解の位置、OCR あり） | 39〜55 秒（1 枚 7〜9 秒） |
| 　うち文字の読み取り（`_read_text`） | 36 秒（9 割） |
| 　うち配線の検出・結び付け・端子間の接続など | 合わせて 3 秒 |
| YOLO の読み込み（プロセスで 2 回目以降） | 0.05 秒、最初の推論 0.45 秒 |

画面の操作とシミュレーションは遅くない。時間と計算のほとんどは文字の読み取り（RapidOCR）で、DD-0012 の DGX の測定
（1 図面 39 秒のうち OCR 35 秒）と同じ傾向だった。OCR のスレッドの数（onnxruntime の intra-op 1・2・4、既定）を
変えても、読む文字も時間も変わらなかった（20.3〜22.7 秒）。

同じ図面の解析し直しは多い。モデルを学習し直した後の全図面の解析（DD-0039）、1 枚ずつの解析のやり直し、
シート番号の候補、ラベルの候補（`label_link_service`）は、同じ画像の同じ場所を毎回 OCR していた。ページのタイルは
検出のモデルによらず同じ画素で、記号の枠も同じ位置なら同じ画素になる。合成図面 6 枚の 1 回の解析でも、
OCR の呼び出し 110 回のうち 29 回は前と同じ画素だった。

ほかに、シート番号の候補（`sheet_number_service`）は呼ぶたびに RapidOCR を作り直し（モデルの読み込み約 0.15 秒）、
図面の向きの判定（`page_orientation`）は解析と別の RapidOCR をもう 1 つ持っていた。

## 2. 変更

- `analysis/ocr_cache.py`: OCR の結果を、読んだ画素・形・呼び出しの引数（`use_det` など）・OCR の版と文字認識の重みの
  ハッシュをキーにして、データフォルダの `ocr_cache/` に JSON で残す `CachedReader`。RapidOCR と同じ呼び方で、
  同じキーなら OCR を呼ばずに前の結果を返す。結果は OCR が返す値そのもの（list・float・str）で、JSON から読み戻した
  値は元と同じ（float は repr で往復する）。書けない・壊れているときは OCR を実行する。
- アプリの起動（`main.py` の lifespan）で置き場を決めたときだけ働く。評価のツール（`eval_suite.py` など）は置き場を
  決めないので、いつも OCR を実行する。止めるときは `SEQANNO_OCR_CACHE=0`。上限は `SEQANNO_OCR_CACHE_MB`
  （既定 1024 MB。1 図面で数百 KB）で、起動時に超えていれば最後に使った時刻の古いものから 8 割まで消す。
- 残す対象: 解析の RapidOCR（ページのタイル・記号の枠の拡大読み・罫線の文字の確認・解析の中の表の欄の読み直し）、差し替えた
  文字認識（`SEQANNO_OCR_REC_MODEL`）、日本語の名称の読み直し（`name_ocr`）。ローカル LLM の読み直しは対象外。
- `analysis/wiring/ocr.py` の `shared_reader`: 図面の向き・シート番号も解析と同じ RapidOCR を使う（モデルを
  2 組読み込まない・呼ぶたびに作らない）。OCR のライブラリを読み込めない環境では、作った後でも ImportError にする
  （これまでどおり「OCR を使えない」と返す）。差し替えた文字認識の RapidOCR も図面ごとに作らず使い回す。
- `tests/test_structure_api.py`: 裏の解析を始めたまま終わっていたテストが、次のテストの DB の作り直しと重なって
  タイミングで失敗することがあった。終わるまで待つ。

## 3. 確認

| 確認内容 | 方法 | 結果 |
| --- | --- | --- |
| 解析の結果が変わらない | 合成図面 6 枚を、置き場なし・空の置き場・2 回目の 3 通りで解析し、構造 JSON 全体のハッシュを比べる | 3 通りとも同じ（`8535ef55c990a103`） |
| 解析し直しの時間 | 同じ 6 枚 | 置き場なし 46.6 秒、1 回目 42.5 秒（同じ画素の重複を省く）、2 回目 6.1 秒（約 7.6 倍） |
| 配線の精度 | `eval_suite.py --only drawings`（40 枚、clean・scan・scan_hard） | 15 指標とも基準値と同じ（scan_hard の回路一致 92.5% など） |
| 置き場の動き | `analysis/tests/test_ocr_cache.py`（同じ画素は 1 回、画素・形・引数・モデルが違えば読み直す、壊れた中身、何も読めなかった結果、上限で古いものから消す） | 成功 |
| テスト | `pytest`、`ruff check .` | 638 件成功・17 件スキップ、指摘なし |

最初の解析の時間はほとんど変わらない。受領図面のように文字の多い図面では、解析し直しの短縮はもっと大きい
（DD-0012 の ER21315 では 39 秒のうち OCR が 35 秒）。

## 4. 残課題

- 最初の解析を速くするには、OCR の量を減らす必要がある（記号ごとの拡大読みは、RapidOCR が短い辺を 736 px まで
  拡大して文字の位置を探すため、小さな枠ほど無駄が大きい。DD-0012 §4）。読む文字が変わるので、受領図面のラベルの
  正解で確かめてから決める。
- 記号の検出の YOLO は解析のたびに読み込む（0.5 秒ほど）。解析全体から見て小さいので変えていない。

## 5. ロールバック

`SEQANNO_OCR_CACHE=0` で残さず、毎回 OCR する。本 DD の差分を revert してもよい。データフォルダの `ocr_cache/` は
消してよい（次の解析で作り直す）。保存データ・API・構造 JSON の形は変えていない。
