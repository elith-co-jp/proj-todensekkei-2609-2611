# DD-0045: システム全体の不具合の洗い出しと、網羅率 100% のテスト

- 状態: レビュー中
- 作成日: 2026-11-22
- 関連文書: [DD-0037](DD-0037-ci-and-circuit-elements.md)、[DD-0039](DD-0039-analysis-jobs.md)、[DD-0040](DD-0040-exe-layout.md)、[DD-0042](DD-0042-db-read-path.md)、
  使い勝手の点検（2026-11-22、プロジェクトの共有フォルダ `usability-review/usability-review-20261122.md`）

## 1. 目的

- システム全体（API・サービス・解析の実行部分・画面）を動かして不具合を探し、直す。
- 不具合が戻らないよう、テストで製品のコードの全行・全分岐を通す（網羅率 100%）。
  網羅率の数字を作るためのテストではなく、本物の部品（PDF・OCR のモデル・SQLite・ngspice・HTTP）で
  振る舞いを確かめるテストにする。
- 受領する図面はスキャンで正解が無く、EXE で各 PC に配るため、テストも外部のサービスに頼らない。

## 2. 直した不具合

| 箇所 | 不具合 | 直し方 |
|---|---|---|
| 回路検証のタイマー | 「実行」を押すと画面全体が落ちる。API が初期状態・終了の記録の `changes` を `{}` で返し、画面は配列を前提にしていた | `{"coils": [], "loads": [], "contacts": []}` にそろえ、画面も欠けた値で落ちない。実際の API の応答で画面の見本を突き合わせるテスト（`tests/test_api_contract.py`）を足す |
| 図面一覧の AI 解析 | 一覧・登録直後・解析結果の再解析が裏のジョブ（DD-0039）を使わず、画面がふさがり、1 枚の失敗で全部が保存されない。コネクタのしきい値の既定が画面ごとに違う | 裏のジョブに替え、進み具合と中止を出す。しきい値の既定（0.6）を `api/defaults.ts` の 1 か所から渡す |
| EXE の自動終了 | 学習中・同期の解析中でも、画面からの合図が 5 分途切れると終わる | `services/busy.py` で実行中の処理を数え、終わるまで待つ。`/api/health` に `busy` を返す |
| 画面の例外・違う URL | 開発者向けの英語の画面が出る | 日本語のエラー画面（`ErrorPage`）を全ルートに付ける |
| 条件タブ | 入力の状態を変えても結果が古いまま | 変えたら計算し直す。操作タブの ON / OFF を初期値にする |
| 押しボタンの出どころ | 図面上の押しボタンも「外部入力（図面範囲外）」と出る | 「押しボタン（入力）」と出す |
| 変更タブの試行 | 発振が直る変更でも「違いはありません」と出る | 警告（発振など）の増減も動作の違いに含める |
| DB の移行（DD-0042） | 重複した索引を消すと、その索引が表の定義に足され、次の起動の `create_all` で作り直される | `DROP INDEX` を直接実行する |
| 学習の採用判定 | 成果物のモデルを消した学習を判定すると「完了した学習ジョブのみ」と誤った理由を返す | 「成果物のモデルが削除されているため判定できません」を返す |
| 学習の出力先 | DB を作り直すと学習の番号が 1 から振り直され、前の DB の `best.pt`・`results.csv` を新しい学習の結果として取り込む | 学習の前に出力先を空にする |
| エディタの下書き | 属性に配列が入った下書きを、正しい属性として復元する | 配列は属性として扱わない |
| 文言・配置 | AI 取込の案内、電気の計算の回数の言い方、タイマーのタブの折り返し、1024px でエディタのツールバーが切れる、入出力の対象の表示 | [UI_WORDING.md](../UI_WORDING.md) のとおりに直す |

点検で見つけたもののうち、次は今回は直していない（仕様を決める必要があるため）。回路検証とエディタの往復で状態が消える（#6）、
変更タブは JSON を手で書く（#8）、「配線」が 2 つの意味で使われている（#10）、一覧の既定の並び順（#16）、DD の状態の意味（#18）。

## 3. テストの方針

- 純粋な関数は、境目の値をそのまま入れて呼ぶ（配線の検出・結び付け・成立条件の式・文字の規則など）。
- API は FastAPI の `TestClient` と本物の SQLite で呼ぶ。失敗の返し方（存在しない図面・壊れた ZIP・前提の欠け）も確かめる。
- 外部の部品は本物を使う。PDF は PyMuPDF で作って PyMuPDF と Poppler の両方で画像にする。OCR は RapidOCR に同梱の
  認識モデルで読む。LLM（Ollama 互換）はテストの中で本物の HTTP サーバーを立てて問い合わせる。回路は ngspice・Lcapy・SKiDL で解く。
- 置き換える（偽物にする）のは、入れると重いか結果が揺れる外部のエンジンだけ。YOLO（ultralytics）、OCR の検出が
  結果を左右する一部の場合、`os._exit` と uvicorn の起動。
- 画面（vitest）は API の応答の見本を使い、その見本が実際の API の応答と同じ形かを pytest で突き合わせる
  （`tests/test_api_contract.py`。画面の API クライアントの呼び先がサーバに実在するかも確かめる）。
- 届かない分岐（呼び出し元が必ず満たす条件の確かめ直しなど）は、テストを作らずにコードから消し、消した理由をコメントに残す。
  研究用の設定でだけ通る分岐（`analysis/tools` から渡す端子の決め方・つなぎ方の選択肢）は消さず、選択肢ごとにテストする。

## 4. 網羅率の数え方

| 対象 | 数える範囲 | 数えないもの（理由） | 基準 |
|---|---|---|---|
| バックエンド | `pyproject.toml` の `[tool.coverage.run]`。ルートのモジュール（`main.py`・`desktop.py` など）、`routers/`、`services/`、`analysis/` の実行部分（`runtime`・`wiring`・文字の読み取りなど） | `analysis/tools`・`analysis/ui`・`analysis/synthetic_circuits`・`scripts`（研究・評価・データ作りの道具で、EXE に入らない。評価は CI の `eval_suite --quick` で回す） | 行・分岐とも 100%（`fail_under = 100`） |
| 画面 | `frontend/src` の全ファイル（`vite.config.ts`） | `main.tsx`（`#root` に描くだけの入口。ルートは `routes.tsx` でテストする）、`types.ts`（型の宣言だけ） | 文・分岐・関数・行とも 100% |

- `# pragma: no cover` などの除外の印は使っていない。EXE の入口（`desktop.py` の `__main__`）も `runpy` で実行して確かめる。
- 任意の依存（Lcapy・SKiDL・RapidOCR・jsonschema・ngspice・Poppler）が無い環境では、その部分のテストは飛ばされ、
  網羅率は 100% に届かない。網羅率を測るときは `requirements-coverage.txt` と `requirements-interop.txt`、OS の
  `ngspice`・`poppler-utils` を入れる（CI の backend ジョブはそうしている）。
- 実行: `make coverage`（`python3 -m pytest --cov` と `npx vitest run --coverage`）。

## 5. 確認

| 対象 | 方法 | 結果 |
|---|---|---|
| バックエンド | `python -m pytest --cov`（Python 3.11、任意の依存あり） | 全テスト成功、製品のコードの行・分岐 100% |
| 画面 | `npx vitest run --coverage` | 33 ファイル・387 テスト成功、文・分岐・関数・行 100% |
| 静的検査 | `ruff check .`、`npx tsc -b` | 指摘なし |
| CI | `.github/workflows/ci.yml` | backend は網羅率つきの pytest、frontend は網羅率つきの vitest。どちらも 100% を下回れば失敗する |

## 6. 残る課題

- CI は Python 3.12 で動く。版によって通る行が変わる箇所が見つかれば、その版のテストを足す。
- 実際の顧客の図面（スキャン）での精度は、正解データが無いため、このテストでは確かめていない（合成図面の評価は DD-0038）。
