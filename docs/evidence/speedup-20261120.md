# 処理の高速化（2026-11-20）

機能を変えずに速くすることを条件に、図面の登録から回路の画面までを実測し、時間のかかる順に直した。
3 つの変更とも、出力が改善前と 1 ビットまで同じになることを確かめた。

## 計測した処理と時間（改善前 → 改善後）

| 処理 | 改善前 | 改善後 | 短縮 |
|------|-------:|-------:|-----:|
| 図面の解析（記号の検出・配線・文字の読み取り。合成図面 6 枚、API `/api/ml/analysis/run`） | 44.0 秒 | 28.6 秒 | 35% |
| 合成回路 60 件の検証（`validate_circuit_logic.py --seeds 60 --faults 3`。シミュレーション・矛盾チェック・波及範囲） | 140.6 秒 | 88.4 秒 | 37% |
| 回路のシミュレーション・もしも・波及範囲など（12 回路の出力を比べる計測） | 5.1 秒 | 3.2 秒 | 37% |

- 環境: 4 コアの Linux、CPU のみ。図面の解析は Python 3.12・RapidOCR 1.4・YOLO（同梱の yolo11s）で、1 枚目を除いた（モデルの読み込みを含めない）。
- 図面の解析の残り 28.6 秒のうち約 19 秒は文字の読み取り（OCR）そのもの。読み方を変えると読める文字が変わるので触れていない。
- PDF の登録（6 枚 約 3.4 秒）、回路の画面の各 API（1 回 0.01〜0.08 秒）はもともと短く、変えていない。

## 変えたこと

1. **回路のシミュレーション**（`services/circuit_model.py`）
   - シミュレーションは状態が落ち着くまで何度も回路を解く。毎回ネットリストの文字を作って読み直していたのを、
     接点の開閉だけ差し替えて同じ行列を作るようにした（`_MnaPlan`）。行列へ足す順と値（`:g` で丸めた値）を文字の場合と
     そろえてあるので、解は浮動小数点の 1 ビットまで同じ。文字にすると行の分かれ方が変わる名前（改行など）や、
     ngspice が入っている環境では従来どおり文字を経由する。
   - ノード名の SPICE 名への変換（正規表現）を覚えておく。ngspice の場所の検索（`shutil.which`）を PATH ごとに 1 回にする。
2. **配線の検出**（`analysis/wiring/detect.py`）: 線の候補を探す 1 画素ずつの走査（1 枚あたり約 1 秒）を numpy にした（約 0.02 秒）。
   見つける線とその順は同じ。
3. **文字の読み取り**（`analysis/wiring/ocr.py`）: RapidOCR を図面ごとに作り直していたのを、1 つを使い回すようにした。
   作り直すたびに最初の読み取りが遅くなっていた分（1 枚あたり約 1.7 秒）が無くなる。

## 機能が変わっていないことの確認

- 図面の解析: 合成図面 6 枚を API で登録・解析・AI 取り込み・保存し、回路の各画面（組立・シミュレーション・矛盾チェック・
  逆引き・波及範囲・もしも・コード・変更の文脈）を呼んだ結果（構造 JSON 全体を含む 530 KB）が改善前と完全一致。
- 合成回路 60 件の検証: `report.json`（秒数を除く）が改善前と完全一致。
- テスト: Python 505 件（3.13）／508 件（3.12、実 OCR・YOLO あり）、画面 98 件、画面のビルドが通る。
  高速化した 2 か所が元の計算と同じ結果を返すことを `tests/test_speedups.py` で確かめる。
- 評価用 30 枚の配線の再現率／適合率: 正解データがこの環境に無いため流していない。配線の検出で変えたのは走査の部分だけで、
  ランダムな画像 1,200 通りと合成図面で元の走査と同じ結果になることを確かめた。
